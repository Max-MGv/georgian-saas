# 17. Edit after the fact — the stale-money check (Chunk 6)

**Status:** ✅ Passing (1/1, 45.4s) — the spec's assertions are written against the *actual*, confirmed-buggy behaviour, not an idealized one; see [[KnownBugs]] #64.
**Tier:** 5 — real staging E2E (`playwright.staging.config.ts`, targets `https://staging.vineworks.ge`, dev DB).
**File:** `tests/tier5-payment-e2e/payment-edit-after-payment.spec.ts`
**Helpers:** existing `auth.ts`/`payments.ts`/`bookingForm.ts`/`flittPayment.ts`/`credentials.ts`/`resendCheck.ts`, plus one new helper — `tests/helpers/orderMoneyDb.ts` (see below).
**Run with:** `npx playwright test --config=playwright.staging.config.ts tests/tier5-payment-e2e/payment-edit-after-payment.spec.ts --workers=1` — mutates the "Individual bookings" payment-section toggle, same discipline as Chunks 3/4.

## Why this exists

The plan's own §4 dependency map flagged the suspect before this chunk started: `updateOrderEnhanced` (`app/actions/orders.ts`) recomputes `Order.totalPrice` (and the rate snapshots) whenever an admin edits guest counts/extras on an existing order — but reading the function in full first confirms it never once references `tx.payment`. `Payment.amount` is written exactly once, at `startCheckout()` time, and after that is only ever *read* — `settle.ts`'s own amount-equality gate, checked once, at the original settlement callback, never re-checked against a later edit.

This chunk went in explicitly expecting to find that gap, not to confirm there isn't one (per the plan's own instruction). **It found it — a real, previously-undocumented bug**, not a false alarm. See [[KnownBugs]] #64 for the full write-up; the rest of this note covers how the spec proves it.

## What the spec does

1. **A real gateway settlement** — same shape as Chunk 3's individual-booking scenario, reused verbatim: turns on "Individual bookings," submits a real Tasting+Lunch booking for 4 guests, pays with the approved non-3DS Flitt test card, confirms the customer-facing "Payment received" screen. This produces a genuine `Payment{ provider: 'flitt', method: 'CARD', status: 'approved' }` row with its own frozen `amount` — not a manually-recorded payment, which the plan is explicit has to be the starting point here.
2. **Captures a BEFORE snapshot** across every §4 surface for this order, plus the one fact none of them show — `Payment.amount`, read directly from the dev DB via the new `orderMoneyDb.ts` helper (a plain, read-only `PrismaClient` against the same `DATABASE_URL` the app itself uses, same pattern `scripts/audit-money.ts` already follows). Confirms the baseline: right now, `Order.totalPrice` and `Payment.amount` agree exactly, in tetri, down to the integer.
3. **The edit** — through the real admin "Guest Breakdown" panel on the order's own detail page, exactly the flow a real admin would use: raises "Total guests in the party" from 4 to 6 and "Tasting+Lunch guests" from 0 to 6 (this order was originally unsplit, so the split has to be filled in at all for `updateOrderEnhanced`'s own `totalPayingGuests > 0` guard to recompute anything — leaving the split at 0/0 and only raising the party size would silently *not* reprice, a real nuance of this function worth knowing but not what this chunk is testing), then clicks "Save changes." The manual per-person rate boxes are left untouched — they're pre-filled from this order's own frozen rate snapshot (`OrderDetail.tsx`'s `manualLunchRateStr` initialises from `order.lunchRateSnapshot`, not a fresh tier lookup, since an individual order has no company tier to look up in the first place) — so this is the most realistic, most sympathetic version of this edit a real admin would make: more guests at the *same agreed rate*, not a rate change layered on top.
4. **Captures an AFTER snapshot**, the identical checks, via a genuine cross-page navigation back to the detail page (not a same-URL `page.goto()`, which `ARCHITECTURE.md`/`theme.ts`'s own note documents as a soft client-side nav that can silently reuse a stale RSC payload) — so what's checked is what the server actually persisted, not the page's own still-live client state from the edit.
5. **Re-sends the invoice** — the one remaining §4 surface, and the only one that involves composing a fresh message rather than just re-rendering a stored number — and reads its actual HTML body via Resend's API (not just "was it sent").
6. **Asserts on the actual, confirmed divergence**: `Order.totalPrice` changed (a real repricing happened, not a no-op), the `Payment` row is the same single row from step 1 (nothing new was created), `Payment.amount`/`status`/`settledAt` are all byte-for-byte unchanged from before the edit, and every UI-visible surface — admin orders table, order detail's own Total card, CSV export, the re-sent invoice — shows the *new* total, not what was actually charged. Numeric comparisons throughout, not string-matching against a hardcoded format, since the edit's arithmetic (original per-person rate × 6 guests instead of × 4) isn't guaranteed to stay a whole-GEL amount just because the original booking was.
7. **Cleanup**, in a `finally` block regardless of pass/fail: deletes the test order via the normal admin UI (cascade-deletes its `Payment`/`OrderEvent` rows, per `schema.prisma`'s `onDelete: Cascade` on `Payment.order`), restores the "Individual bookings" toggle, and disconnects the Prisma client the DB helper opened (otherwise a long-lived connection keeps the Playwright worker process alive past the test).

## New helper: `tests/helpers/orderMoneyDb.ts`

Every other tier5 helper drives the real UI or an external API (Resend). This one is different on purpose: it's a direct, read-only Prisma read against the dev database, because `Payment.amount` is the one fact in this entire dependency map with **no UI surface anywhere in the app** — confirmed again while building this spec with a fresh grep for `payment.amount` outside `settle.ts`/`manualPayment.ts`/a read-only audit script, same conclusion the plan's own research already reached. A Playwright assertion against the rendered page can never, by itself, prove whether `Order.totalPrice` and `Payment.amount` have diverged — only a direct read of the row can, which is exactly what this chunk exists to do reproducibly, not just once by hand.

It loads `saas/.env`'s real `DATABASE_URL` via `dotenv` and reuses `@/lib/db`'s own `PrismaClient` singleton — the same connection the live app uses, the same dev Supabase project every other chunk's manual verification already reads from. Read-only by design: nothing in this helper writes.

## The result: a genuine, previously-undocumented bug

Confirmed, not assumed, and independently reproduced on **three separate live runs** (see "Getting to a clean pass" below — each failed run's leftover data was inspected via direct SQL before cleanup, and all three showed the identical shape): a real individual booking (Tasting + Lunch, 4 guests) settles for **480₾** (`Payment.amount = 48000` tetri, `Order.totalPrice = 48000` tetri — exact agreement). After raising the guest count to 6 through the real admin UI at the *same* per-person rate: `Order.totalPrice` becomes **720₾** (`72000` tetri) on every single UI surface checked — the admin orders table, the order's own "Order Total" card, the CSV export, and a freshly re-sent invoice email — while the same `Payment` row's `amount` stays exactly `48000` tetri, `status='approved'`, `settledAt` byte-for-byte unchanged. **Nothing anywhere in the app flags this ₾240 disagreement.** There is no payments list screen, no reconciliation check, no warning badge — an admin looking at this order's own detail page, the orders table, or the CSV would see one consistent (but wrong) number everywhere, with zero indication that a real customer's card was only ever charged a smaller amount. Full write-up: [[KnownBugs]] #64.

## Getting to a clean pass — two real test bugs, both about a locator outliving a navigation

Four runs total, the first three all failing on `test.setTimeout` (200s, 300s, then 400s) despite the underlying app behaviour being exactly as described above every single time — confirmed via direct SQL after each failure, before that run's leftover order and toggle state were cleaned up by hand (via the real admin UI/Settings page, the same mechanism the spec's own cleanup uses) ahead of the next attempt:

1. **Runs 1–2 — a missing navigation before "Send Invoice."** `exportOrdersCsvViaUi`'s own internal `page.goto('/admin/orders')` (run for the post-edit CSV export) left `page` on the orders table, and the very next step tried to click "Send Invoice" — a button that only exists on the order's own detail page. A Playwright locator action's default timeout is unbounded when neither `use.actionTimeout` nor a per-call `timeout` is set (it inherits the *test's own remaining budget*, not a fixed ~30s), so the click just retried silently against a button that would never appear, consuming the whole run. Fixed with an explicit `await page.goto(detailUrl)` before the invoice section.
2. **Run 3 — the identical failure shape, one step later.** With `mark()` timing added (see the spec's own `mark()` calls), this run's log showed every real step succeeding, including the invoice re-send, up to +41s — then nothing. Root cause: `rowAfter` (a `Locator`) was built while `page` was on `/admin/orders`, but by the time it was read again (deep in the final assertion block, checking the admin-table total) `page` had since navigated to the detail page for the invoice re-send (fix #1, above). Same unbounded-timeout hang, different stale locator. This is exactly why the `mark()` timings mattered: without them, "some step near the end is slow" and "a stale locator on the wrong page is hanging forever" look identical from the outside. Fixed by moving that read to the one point `page` is actually still on `/admin/orders` — right after the second CSV export, before the detail-page navigation for the invoice.
3. **Run 4 — clean.** 1/1 passing in 45.4s, confirming the earlier "this scenario needs 5+ minutes" assumption was itself wrong — the real work was always fast; runs 1–3 were each burning their entire budget on one broken locator, not genuine cumulative latency across the real Flitt checkout / CSV exports / Resend round trip. `test.setTimeout` was trimmed back down to a still-generous 200 000ms accordingly.

**The general lesson, worth carrying into any future spec that navigates more than once:** a `Locator` is not a snapshot — it re-resolves against whatever `page` is currently showing at the moment it's used, not the page it was defined against. Capture a value from a locator immediately, on the same page it's valid for, rather than holding the `Locator` object across a later navigation and reading it there.

## Whether this test's assertions pass or fail

**They pass** — deliberately asserting on the real, confirmed, buggy behaviour, per this chunk's own instructions ("do not quietly adjust an assertion to match reality — if you find a discrepancy, the spec should prove it's real and reproducible"). A future fix to `updateOrderEnhanced` (or a decision to add a reconciliation surface) would need this spec's assertions rewritten deliberately, not silently broken — the same "loud, not silent" spirit the settlement-email known-bug annotation in `13-payment-approved-settlement.md` already established for this suite.
